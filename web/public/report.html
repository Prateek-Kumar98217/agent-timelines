What editing a step changes

Each of 8 tasks ran once on qwen3:4b, then each kind of edit was forked from it twice: 136 branches in all. Models vary between runs with no edit at all, so no-op forks set the baseline. An answer counts as diverged when its similarity to the source falls below 0.957, the 10th percentile of those no-op forks.

* Editing the task itself isn't possible in the product. These forks went through the engine directly, and they measure how sensitive the model is.

Similarity follows wording, not facts. A contradicting source changed the facts in 62% of runs, yet only 7% counted as diverged, because a changed date barely moves the score. That's why the compare view marks the changed words.

7 of 8 original runs got every required fact. Those runs took 4 to 6 turns. 135 of 136 branches completed. The other failed after the model hit its 2-minute call limit three times on one step, which is the retry limit working as designed. Samples are small, so read the intervals rather than single percentages. Convergence is based on one model and 8 tasks.

LLM as a judge

The judge agreed with the deterministic fact check on 6 of 6 answers. With so few, this shows the two checks don't obviously conflict. It doesn't show the judge is accurate in general.

Failure checks on the running stack

Run from scripts/smoke_local.py and scripts/smoke_observability.py, in containers, with a scripted model.

  • 20 parallel forks, with a stream of events showing no gaps
  • 30 of 40 simultaneous forks accepted at a limit of 30, with the other 10 refused
  • A worker killed mid-step: the branch resumed with no duplicate or missing steps
  • The message broker stopped: nothing lost, and the branch finished after it returned
  • The message broker killed during a send: the step wasn't lost
  • A waiting branch: no queue message and no active worker
  • The browser container: no route to internal services, no secrets, no access to agent tools
  • A saved API key: absent from every log, trace and metric
  • A website pointing its domain at this machine: refused
  • One trace across the API, worker and gateway, with all 12 dashboard panels returning data

The log check failed on GitHub. Loki refuses all writes once its disk is 90% full, and it reports this as "Ingester is shutting down". Forcing that limit locally reproduced the same failure. The job now frees disk space before it builds, and CI passes on GitHub with this fix and the one below.

CI found a real bug. A step was marked as sent without the broker confirming it, so a broker dying at that moment lost the message and left the branch stuck for 5 minutes. Sends now wait for confirmation, which is why forks in the load test above got slower under heavy load. A request can now wait about 6 seconds if the broker stops answering.

Live checks with the real model

Run once by hand on the full stack, with qwen3:4b.

Web fetch into the task's RAGA real page from example.com was stored with its source, split into 2 chunks.
Search after the fetchA real task_search through the MCP gateway returned that page.
Search from before the fetchThe same search on a fork from before the fetch found nothing, so the path rule holds.
Editing a fetched pageThe fork saw only the edited page, the model answered from it, and the original branch's store was unchanged.
Continuing a branchA finished branch took another message and answered, using the page it had already fetched. One with no turns left gained 4, and one with turns left gained none.
Editing the taskThe API refused it with a 409.

The model rarely searches. It answered from the fetched page without calling task_search, even when the task asked for it, so the search above was triggered with an edit. On short tasks with this model, the task's RAG often goes unused.
